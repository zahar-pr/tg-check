# Как устроен код

Разбор для того, кто открыл проект впервые. Без списка функций — его видно и
так. Здесь про то, чего по коду сразу не понять: почему сделано именно так и
где лежат неочевидные решения.

Сопутствующее чтение: [HANDOVER.md](HANDOVER.md) — доступы и выкладка,
[TECH-BASE.md](TECH-BASE.md) — подробности про ограничения Telegram.

---

## Главная мысль

**Панель ничего не делает с Telegram сама.** Она — диспетчер: запускает
Python-скрипты по одному на аккаунт, читает их вывод построчно и решает, когда
звать аккаунт снова.

```
браузер → router.mjs → admin.mjs → python-скрипт → Telegram
           привратник    панель       задача        (через прокси)
```

Из этого следует почти всё остальное устройство:

* **Состояние живёт в файлах, а не в памяти.** Перезапуск панели не теряет
  ничего: кто что написал, у кого кончилась квота, где остановился прогрев —
  всё в CSV и JSON рядом с панелью. Поэтому выкладка безопасна.
* **Задача общается с панелью одной строкой.** Последняя строка вывода —
  `⌁STATE {json}`: сколько сделано, сколько осталось, не придержал ли Telegram
  аккаунт и на сколько. Остальные строки идут человеку в журнал.
* **Один аккаунт — одна задача за раз.** Сессия Telethon — это файл SQLite,
  два процесса на одной сессии дают `database is locked`.

## Три слоя

### Привратник — `router.mjs`

Занимает публичный порт и держит по процессу `admin.mjs` на каждый профиль.
Спрашивает логин, по нему понимает, чей это профиль, и передаёт запросы
нужной панели.

Два решения, которые стоит знать:

* **Куку браузера панели профиля не передаём.** Вместо неё — одноразовый ключ,
  выданный этому процессу при запуске (`TG_PANEL_TOKEN`). Панель слушает только
  `127.0.0.1`, снаружи к ней не подойти.
* **Заголовок `Origin` дальше не идёт.** Привратник проверяет источник у себя.
  Если переслать его как есть, панель профиля сверит его со своим внутренним
  адресом, не найдёт совпадения и отобьёт любой POST. Так уже было — отсюда и
  комментарий в коде.

Профили поднимаются при старте и перезапускаются, если упали, — иначе прогрев
и рассылка шли бы только пока кто-то смотрит в браузер.

### Панель — `admin.mjs`

Три тысячи строк, в начале файла карта с номерами строк. Условно делится так:

**Выше раздела HTTP — как панель работает.** Реестр задач (какой скрипт за что
отвечает), запуск задач, прогрев, автопрогон рассылки.

**Ниже — что она отвечает браузеру.** Статика, вход, шесть десятков маршрутов
API, разбитых по подразделам.

Проверка и письмо — **одна цепочка, а не две пачки**. Пока аккаунту сегодня
есть что написать, он берёт ровно один номер: нашёл живого — следующим шагом
сразу пишет ему, не нашёл — берёт следующий. Между шагами пауза как между
номерами внутри пачки, а долгий отдых — когда аккаунт выдал свою порцию писем
(`writeLimit`). Пачкой номера проверяются только когда писать нельзя: режим
«только проверять», ночь, выбран дневной предел.

Самое неочевидное место — **автопрогон**. Это не цикл «идти по базе», а
планировщик: раз в несколько секунд он смотрит, кого можно позвать, и решает,
какую задачу дать. Учитывает дневные потолки, возраст аккаунта, рабочее время,
закрытую квоту контактов, занятость аккаунта, живость прокси и ручные действия
человека (любая задача, запущенная руками, ставит автоматику на паузу).

### Задачи — Python

Каждая делает одно дело и выходит. Общее — в `tglib.py`: подключение с прокси,
реестр аккаунтов, разбор ответов SpamBot, работа с папками Telegram, имена,
пути к данным профиля.

Пути — отдельная история. `tglib.CODE` — где лежит код, `tglib.DIR` — папка
данных профиля (её задаёт переменная `TG_PANEL_DIR`). Образцы вроде
`warm-list.default.json` берутся из кода, всё остальное — из данных профиля.
Без переменной всё работает по-старому, в одной папке.

## Что где лежит в вебе

`web/index.html` — вся разметка, экраны секциями `data-view`.
`web/app.js` — вся логика, в начале карта с номерами строк.
`web/app.css` — оформление.

Сборки нет намеренно: файлы читаются с диска на каждый запрос, поэтому правку
интерфейса можно выложить **без перезапуска панели** — работа не прервётся.
Плата за это — браузерный кеш: поправил `app.js`, подними версию `?v=rNN` в
`index.html` и `profiles.html`.

Экраны рисуются опросом раз в две секунды. Перерисовка только при изменении
разметки — иначе пропадал бы фокус в полях и дёргались списки.

## Два набора получателей

Панель умеет работать «по номерам» и «по чатам». Это разные списки, разные
файлы и разные вкладки:

| | по номерам | по чатам |
|---|---|---|
| откуда люди | файл с номерами | разбор групп и каналов |
| нужна ли проверка | да, «есть ли Telegram» | нет, они уже там |
| квота контактов | тратится | не тратится |
| файлы | `numbers.csv`, `results.csv`, `drafts.csv` | то же самое в `chats/` |

**Набор — свойство аккаунта, а не панели.** Каждая вкладка рассылки запускает
свой режим со своим составом: девять аккаунтов могут идти по чатам, а
остальные в это же время — по номерам. Режимы заканчиваются независимо, и
«Остановить» на вкладке гасит только её.

Общее у режимов одно, зато главное — **прокси**. Поэтому очередь запусков,
работа по одному аккаунту за раз и смена IP остаются общими: два режима не
удваивают нагрузку на один адрес. Один аккаунт работает в одном наборе за раз
— иначе он делил бы дневной предел надвое и путал бы свои очереди.

`base-set.json` остался, но теперь он только про ЭКРАНЫ: какую базу и какие
результаты смотрит человек. На прогон он не влияет.

Как это устроено в коде: `auto.sets` — кто в каком наборе, `auto.opts` —
настройки каждого режима, `auto.live` — какие режимы работают. `work(set)`
считает остаток работы по своему набору, `pickJob` берёт настройки через
`optOf(id)`. Задачам набор передаётся переменной `TG_SET`.

## Прогрев

Свежий аккаунт, который сразу пошёл писать незнакомым, живёт недолго. Поэтому:
сутки отлёжки, потом постепенный набор объёма.

Две лестницы, обе считаются от даты добавления аккаунта:

* **сколько писем в сутки** — `server/warmup.mjs`;
* **сколько человеческих действий в сутки** (подписки, реакции, группы,
  переписка, боты) — `warmup-activity.py`.

Срок прогрева настраивается в панели (2–21 день), обе лестницы раскладываются
на выбранный срок. Отлёжка в первые сутки не сокращается никогда.

Переписываться аккаунт может **только со своими** — с другими аккаунтами этой
же панели. Если аккаунт один, этот вид действий отпадает: писать некому.
Поэтому для нормального прогрева нужно хотя бы три аккаунта.

## Обогащение: читатели и писатели

Вкладка «Лиды». Ищем в чатах людей, которые хотят квартиру, и пишем только им,
а не всем участникам подряд. Схема ролей — [readers-writers.html](readers-writers.html).

Аккаунты делятся на два пула. **Читатель** (`role: 'read'`) читает чаты: не
греется, не попадает в рассылку и никому не пишет. **Писатель** — обычный
аккаунт рассылки. Жалобы прилетают только писателям, база с читателями не
теряется.

Поток по одному чату:

```
тема → ключевики (модель) → поиск чатов → очередь enrich/chats.json
  → читатель: вступил, 90 дней пачками по 100, вышел     enrich-read.py
  → разбор: каждый автор + по 10 соседних сообщений      enrich-analyze.py
  → лиды в enrich/leads.json и в очередь «по чатам», сырьё удалено, чат done
  → «Написать лидам»: автопрогон по чатам с --leads-only  draft-messages.py
```

Неочевидное:

* **Почему окна, а не ключевые слова.** «А ты хату брать будешь?» — «да»: у
  второго нет ни одного слова про квартиру. Модель видит автора (►) вместе с
  соседями и судит по смыслу. Ответ модели — последний JSON в тексте:
  модели с рассуждениями пишут ход мыслей прямо в ответ.
* **Один чат — один читатель.** Чат выдаёт `enrich.pick_chat` под замком
  файла. Панель очередь только читает, а пишет через `python enrich.py add|retry|remove`,
  чтобы её запись не затёрла запись читателя.
* **Поэтапно.** В работе не больше «читатели + 1» чатов (`server/enrich.mjs`):
  выкачали — разобрали — следующий. Иначе скопились бы гигабайты сырья,
  которые модель разберёт через неделю.
* **Лид без @username.** `access_hash` у каждого аккаунта свой, а читатель
  человека видел, писатель — нет. Поэтому у лида хранятся чат и id его
  сообщений: писатель открывает сообщение и берёт человека «из сообщения»
  (`InputUserFromMessage`, `draft-messages.via_message`). `tglib.can_write`
  отдаёт такого лида любому писателю.
* **Упавший читатель не держит чат.** «Читается» без живого процесса панель
  возвращает в очередь (`python enrich.py release`); остановка из панели
  (SIGTERM) возвращает чат сама и выходит из вступленных чатов.
* **Модель не ответила по автору** — сырьё не удаляем, чат ждёт повтора
  (до трёх заходов): лиды среди «трудных» авторов не теряются молча.
* **Статус лида** («написали», «черновик») не пишется в leads.json, а
  считается по `chats/drafts.csv` — тот же журнал, что у всей рассылки.

Проверка без Telegram и модели: `tests/sandbox/enrich_test.py` (нужен
Telethon) и `node tests/sandbox/enrich_sched_test.mjs`.

## Чего в коде нет и почему

* **Фреймворков.** Ни на сервере, ни в вебе. Панель — один человек за одним
  экраном, собирать ради этого сборку и роутер избыточно.
* **Базы данных.** CSV и JSON читаются с кешем по времени правки. На десятках
  тысяч строк этого хватает, а чинить такие файлы можно глазами и руками.
* **Тестов.** Их правда нет. Питоновские задачи когда-то проверялись на
  «песочнице» с подменённым `tglib.connect` — это стоит вернуть первым делом.

## Куда смотреть, если что-то сломалось

| Симптом | Куда |
|---|---|
| Панель не отвечает | `systemctl status tg-panel`, `journalctl -u tg-panel -n 50` |
| Аккаунт ничего не делает | строка аккаунта в панели: там написана причина — отлёжка, предел, квота, ограничение |
| Задача падает молча | журнал внизу панели, раздел «Журнал — подробности для отладки» |
| `database is locked` | кто-то запустил скрипт мимо панели на том же аккаунте |
| Пропал текст в таблице | проверь окончания строк в CSV (`file` или `cat -A`): `\r\n` ломает имя последней колонки |
| Аккаунт вышел с чужого IP | прокси лёг или сменился в середине задачи — смотри сторож прокси в журнале |
